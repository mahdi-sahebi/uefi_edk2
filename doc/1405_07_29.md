## Why this capture stops short of the menu

`FTWa-3` was emitted immediately before `delay_s(2)` in `FaultTolerantWritePei`. That function performed roughly four billion volatile arithmetic iterations for this one call. Earlier `delay_s(1)` calls also ran. The text file ended during this slow path, while the associated recording later reached DXE Core. Thus `FTWa-3` was not a demonstrated flash-access failure. The recording ends too early to establish a DXE hang or crash.

The two `AcpiTimerLib.c(57)` assertions came from `DelayedDispatchDispatcher()` requesting the time even though its queue was empty. `BlSupportPei`, which creates `gUefiAcpiBoardInfoGuid`, had not yet run. The log continues after both assertions, so they were not the observed stopping point. Coreboot's earlier warnings and assertions also did not prevent the payload handoff. The flash-size mismatch and missing TPM remain separate platform issues to investigate if a later capture shows they affect DXE or BDS.

At text-capture time, coreboot selected ASRock SPC741D8, SMMSTORE v2, SOL UART `0x2f8`, the built-in UEFI Shell, and the EDK2 boot menu. The G4DEL port now has a separate board selection. A new boot capture is required to determine whether the current G4DEL image completes DXE and reaches the menu.

## Changes made

- Removed the FTW artificial busy loops and their VGA-only progress code. FTW now logs HOB contents, working and spare ranges, workspace validation, recovery decisions, and PPI installation to SOL using `[EDK2-DIAG]` markers.
- FTW now checks missing or short HOBs, unsupported HOB versions, failed range lookups, invalid or overflowing ranges, and recovery HOB allocation before dereferencing or publishing data. Its spare scan has a defined lower bound.
- PEI skips time calculation when the delayed-dispatch queue is empty, so those early calls cannot trigger the missing ACPI board-info HOB assertion.
- Added or extended markers for `BlSupportPei` completion, DXE IPL entry and handoff, boot-menu readiness and selection, and Shell initialization. Existing console-connection markers remain in BDS.
- Checked the SMMSTORE geometry and address range before publishing or consuming the variable-flash HOB. Failed SMMSTORE, graphics, and graphics-device HOB allocations now return an error before dereference. Variable FV header length is bounded before checksum and variable-store access.
- The G4DEL payload build uses SOL register base `0x2f8` and disables optional TPM support. The boot manager's PCR-bank prompt and physical-presence calls are compiled only when TPM support is enabled; this also resolves the TPM-disabled link failure found during the first G4DEL rebuild.

The stock BIOS contains AMI/Intel UEFI firmware volumes and `G4DEL110`/Gooxi identifiers. Its executable BIOS and variable store are not used in the new image. The older coreboot ROM kept the ME bytes but altered 13 descriptor bytes and erased the GbE and Device Exp1 regions. This explains a concrete image assembly gap, although it does not prove the PEI stop. The older ASRock board target used `MAX_SOCKET=1` on a dual-socket platform; that is consistent with the coreboot socket assertions. Its GPIO and forced CXL settings are board-specific and are not carried into the G4DEL target.

The coreboot port uses the existing 64 MiB flash map, a separate 256 KiB SMMSTORE v2 region, and the factory descriptor, ME, GbE and Device Exp1 bytes. It starts with Archer City's two-socket IIO table. Physical PCIe routing and the number of empty DIMM slots remain unverified; installed DIMMs are reported from the FSP HOB. The old log's `SF size 0x8000000` conflicts with the known 64 MiB image, so the SPI size warning now includes bus, chip select, JEDEC ID and sector size at error level. No flash-size change is justified yet. TPM is disabled as an optional boot dependency.

For read-only inspection, run `util/ifdtool/ifdtool -p lbg -d /media/sf_shared/server.bin` and `python3 util/g4del_stock.py /media/sf_shared/server.bin` from the coreboot root.
